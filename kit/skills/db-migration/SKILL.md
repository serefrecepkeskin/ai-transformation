# db-migration

A schema change breaks at query time, in production, with no build signal — in this repo, or in another repo of the
workspace that maps the same table. The tool, its commands and who owns the migrations are in the repo's
`AGENTS.md › Stack & run / Where code goes` and the workspace guide's **Shared data** section; read them first.

## Steps

1. **Only the owner migrates.** If the workspace guide says another repo owns this schema, the change starts there;
   here you only update the mirror after it.
2. **Edit the model first**, following the repo's column conventions (ids, timestamps, soft-delete flags, naming).
   A new model is registered wherever the repo registers models.
3. **Generate the migration with the repo's tool** (e.g. `alembic revision --autogenerate -m "<what>"`). Let the
   tool pick the revision id and set the parent to the current head — hand-picked ids collide.
4. **Read the generated file.** Autogenerate misses renames, partial/unique indexes, CHECK constraints, triggers,
   server defaults for NOT NULL additions and data steps; add them by hand. A data backfill is a separate, idempotent
   migration. Write a real downgrade, or record in the migration why it is irreversible.
5. **Every other reader.** Any repo that maps or queries the table (workspace guide › Shared data, or
   `rg '<table>'` across the workspace) gets its mirror/query updated in the same change set — or is listed in the
   report with what it needs.
6. **Test.** Apply locally on a disposable database, run the test suite, exercise the affected endpoints; the
   repo's drift check (e.g. `alembic check`) is clean.
7. **State the deploy order in the report**: migration first, then the services that read the new column; for a
   DROP the reverse (readers first, then the migration). Name what breaks in the wrong order.

## Do not

- Run a migration against a shared or remote database unless the spec says exactly which one.
- Edit the database by hand, or edit an applied migration.
- Drop or rename a shared column in one step — add, migrate readers, then drop across releases.
- Mix unrelated schema changes in one migration.
