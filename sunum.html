AI Destekli Geliştirme — Şablon

Kurallar, araçlar ve kontroller tek yerde. Tek şablon, iki araç: aynı skill ve ajanları Claude Code ve GitHub Copilot okur. Bu sunum şablonun mantığını ve bir işin baştan sona nasıl aktığını anlatır.

Neden

Hangi sorunu çözüyoruz

Ajanlar hızlı. Ama kurallar herkesin kafasındaysa her ajan farklı iş çıkarır.

Sorun: kurallar dağınık

Her repoda farklı rehber, farklı ayar. Ajan neyi bilmesi gerektiğini bilmiyor.

Çözüm: tek kaynak

Kurallar ve araçlar kit'te. Tek repoda kopya, workspace'te link. Bir yerde değişir, her yerde geçerli olur.

Sorun: review atlanıyor

"Sonra bakarız" deniyor. Kontrolsüz kod PR'a gidiyor.

Çözüm: PR kapısı

Review'lar gerçekten koşmadan Claude git push ya da PR açamaz. CI da PR açıklamasını kontrol eder.

Sorun: şablon koda uymuyor

Genel bir rehber, gerçek repoyu anlatmaz. Ajan tahmin eder, tahmine güvenilir.

Çözüm: bootstrap prompt

Kurulumdan sonra ajan her PLACEHOLDER'ı gerçek koddan doldurur. Doğrulayamadığını TODO(confirm) bırakır.

Kurulum

Üç kurulum hedefi

Tek komut: install.sh <hedef>. Script hedefe bakar, sorar, kurar.

1install.sh <hedef>Bir repo ya da repolardan oluşan bir klasör.
2Hedefi tanır.git var → tek repo. Alt klasörleri git reposu → workspace.
3SorarProfil (manifest'ten tahmin), AI aracı: claude / copilot / both.
4Bootstrap prompt'u basarAjana yapıştırırsın, gerisini o doldurur.

Tek frontend repo

Anlar: package.json.

  • kit dosyaları kopyalanır
  • verify-ui, ui-check, impeccable, frontend-reviewer
  • husky + lint-staged, Playwright e2e iskeleti

Tek backend repo

Anlar: pyproject.toml / requirements*.txt / setup.py.

  • kit dosyaları kopyalanır
  • new-endpoint, db-migration, backend-reviewer
  • pre-commit kapısı

Workspace

Anlar: alt klasörleri git reposu olan klasör.

  • yanına kendi agent-kit reposunu oluşturur
  • kökü kurar, her repoyu profiline göre link'ler
  • her repo: backend / frontend / skip
Sormadan kurmak için: --yes, --tool, --profile, --kit-remote <url>. Boş repo: --new (önce karar, sonra iskelet). Var olan dosyaya dokunmaz; tekrar çalıştırmak güvenli.

Bootstrap

Kurulum sonrası: bootstrap prompt

Kurulan dosyalar geneldir. Bootstrap prompt'u onları bu kod tabanı için doğru yapar — yalnız kanıttan.

1TaraManifest, klasörler, CI, testler, eski belgeler, git log. Önce oku, sonra yaz.
2DoldurAGENTS.md'nin 8 başlığı ve docs/ altındaki her PLACEHOLDER.
3Kapıyı bağlaRepoda lint yoksa gelen ayar esas; varsa onlarınki kazanır. Sonunda tek commit kapısı.
4Ön koşullarHook gerçekten bağlı mı, Node sürümü, sır dosyaları. Eksik → manual-actions.md.
5RaporNeyi nereden doldurdu, açık TODO(confirm)'lar, insana kalanlar.

Demir kural

Yazılan her şey repoda okunmuş bir dosyadan gelir. Doğrulanamayan TODO(confirm): <soru> olur. Görünür boşluk, makul tahminden iyidir.

İki tür dosya

kit'e ait skill, ajan, hook, settings, pr-evidence.yml — burada düzenlenmez. repoya ait AGENTS.md, docs/, kapı dosyaları — doldurmak senin işin.

Workspace'te

Her repoda bir tur, sonra kökte bir kez: platform rehberi (repo haritası, ortak veri, branch'ler), pr-evidence.yml promosyon kuralı, kapının hassas yolları.

Bootstrap bir görev değildir: kod değişmez, agent-work/ açılmaz, commit ve PR yok. Boş repoda başka prompt: install.sh … --new → önce stack kararı, sonra iskelet.

PR kapısı

Push ve PR nasıl kontrol ediliyor

İki yarı var: ajanın bilgisayarında hook, GitHub'da CI.

1Ajan push/PR istergit push ya da gh pr create
2Hook oturum kaydına bakarBu oturumda gerçekten koştu mu?
3Aranan 5 şey/simplify · /code-review · reponun reviewer'ı · güvenlik taraması · review.md

Eksik varsa → durur

Ajan eksik listesini görür: "şu review koşmadı, şu dosya yok". Tamamlar, tekrar dener.

Tamamsa → geçer

Push gider. PR açılınca CI pr-evidence.yml açıklamada ## Nasıl doğrulandı, ## Self-review ve reviewer adını arar.

Güvenlik ajanı ne zaman şart

auth, session, permission, rbac, jwt, secret, password, credential, consent ya da migration dosyası değiştiyse security-reviewer zorunlu. Liste pr_gate.py'deki SENSITIVE; workspace genişletir.

Muaf olanlar

Promosyon/deploy PR'ları: varsayılan production ve release/*'a giden PR'lar. Hook ve CI aynı kuralı uygular; bootstrap workspace'e göre ayarlar.

Oturumlar arası

review.md içindeki ## Gate bloğu sonraki oturumda kanıt sayılır. /commit-and-pr yazar.

SSS

"Kökten başlıyorsak repo içindeki bu dosyalar gerekli mi?"

Evet. Üç sebep.

1. Repo içinden çalışan olur

Biri repo klasöründe claude açarsa orada da izinler, hook'lar ve kapı çalışmalı. Kökün ayarı o zaman uygulanmaz.

2. Copilot repo içinden okur

Copilot rehberi .github/copilot-instructions.md'den, ajanları .github/agents'tan okur. Bulut ajanı yalnız tek repoyu görür.

3. CI repo içinde koşar

pr-evidence.yml GitHub'da her repoda ayrı çalışır. Workflow repoda olmak zorunda.

Profil kuralı: backend repolar new-endpoint, db-migration, backend-reviewer alır; frontend repolar verify-ui, ui-check, impeccable, frontend-reviewer. Ortak: write-spec, implement-task, review, commit-and-pr, security-reviewer. Profil değişirse öbür profilin link'leri temizlenir; reponun aynı adlı kendi dosyasına dokunulmaz.
Workspace'te link'ler ../agent-kit'i gösterir. agent-kit yanında olmayan bir makinede (sunucu, bulut ajanı) link boş kalır — orada tek-repo modu kullanılır.

Reviewer'lar

Reviewer ajanları — soğuk göz

Kodu yazan değil, sadece diff'i ve amacı gören ayrı bir ajan. Dosya değiştirmez, bulgu döner.

backend-reviewer

  • sorgu çağıranın kapsamıyla mı sınırlı
  • izin tanımlı mı
  • katmanlar, async hatalar
  • migration, sözleşmeler, testler

frontend-reviewer

  • menü, route ve buton aynı yetkiyi mi okuyor
  • tek kaynaklı listeler, her dilde çeviri
  • tasarım sistemi kuralları, erişilebilirlik
  • TypeScript sıkılığı, gereksiz karmaşıklık

security-reviewer

  • kapsam ve izolasyon
  • yetki ve devretme kuralları
  • log, prompt, audit satırında kişisel veri
  • rate limit, cache iptali, bağımlılık riski

UI ve testler

Bir ekranın doğru olduğunu nasıl kanıtlıyoruz

"Derlendi, testler yeşil" yetmez. Dört katman var; her biri öbürünün göremediğini görür.

1VitestBileşen ve mantık testleri. Hızlı. Her commit'te.
2Playwright e2eScript tüm ekranları gezer: açılıyor mu, konsol hatası, taşma, üst üste binme, kaydırma. Ajansız.
3verify-uiAjan gerçek tarayıcıda: menüden tıklayarak ekrana ulaşır, butona basar, sonucu görür.
4ui-checkSürüm öncesi: ekran × rol × genişlik × dil matrisi, bug listesi.

Script neyi yakalar

Her ekranda aynı mekanik kontroller. Yorulmaz, atlamaz. Ama "buton doğru işi yaptı mı" diyemez.

Ajan neyi yakalar

Etkileşim, dialoglar, rol bazlı yetki, her dil, "işlev gerçekten çalışıyor mu". Script'in bıraktığını tamamlar. Tarayıcı yoksa "browser smoke pending" der, iddia etmez.

Tasarım

impeccable ne işe yarıyor

Testler arayüzün çalıştığını kanıtlar. impeccable doğru göründüğünü kontrol eder.

1. Skill olarak

Sen ya da ajan çağırırsın. Alt komutları var:

  • audit / critique — tasarım eleştirisi
  • polish — son cila
  • layout, typeset, colorize — düzen, yazı, renk
  • harden, adapt — kenar durumları, mobil

2. Hook olarak (dedektör)

Frontend'de bir UI dosyası değişince kendiliğinden koşar. Bariz hataları anında söyler. LLM kullanmaz, deterministik. Claude'da settings.json, Copilot'ta .github/hooks/impeccable.json.

1UI dosyası düzenlenir.tsx, .jsx, .css…
2impeccable hookDedektör değişen dosyaya bakar.
3UyarıAjan uyarıyı görür, düzeltir.

Neye göre bakar

docs/DESIGN.md: markanın renkleri, yazıları, kuralları. Boşsa impeccable dişsiz kalır.

Nereden geldi

Açık kaynak (Apache-2.0), kit'te tek kopya. Elle düzenlenmez, npx impeccable update ile güncellenir. Karar: ADR 0002.

Bilmen gereken

Hook Node 22+ ister. Workspace kökünden başlatınca hook çalışmaz (kök ayarında yok); skill yine kullanılabilir.

Kurallar

Ajanın her istekte gördüğü 12 prensip

İlk beşi Andrej Karpathy'nin LLM ile kod yazma prensipleri.

1 · Önce düşün

Varsayma, sor. İki okuma varsa ikisini sun. İtiraz et.

2 · "Bitti"yi tanımla

Hangi komut kanıtlayacak? Koşmadan "çalışıyor" deme.

3 · Kapılar yeşil

Hepsi, sayısıyla. Kapı zayıflatılmaz.

4 · Basit

Gerek var mı → repoda var mı → stdlib → … → en az kod.

5 · Cerrahi

Her değişen satır isteğe bağlanır. Komşu koda dokunma.

6 · Kök neden

Semptomu değil, hatanın doğduğu yeri düzelt.

7 · Test

Her davranış değişikliğine test. Bug'da önce kırmızı.

8 · Sınırda doğrula

Dışarıdan gelen veri typed modele girer.

9 · Sırlar

Okunmaz, yazdırılmaz.

10 · İnsana kalanı yaz

Sunucu ayarı, secret, elle migration → rapora + PR notuna + manual-actions.md.

11 · Karar = ADR

Yerleşen karar aynı PR'da docs/decisions/'a.

12 · Başkasına ait metin

Hukuk, uyum, sözleşme metinlerine dokunulmaz.

Belgeler

Belgeler nerede durur, eskiler nasıl taşınır

Ajanın okuduğu belge repoda, insanın okuduğu belge humans/'ta.

agent-kit/platform/ workspace geneli ├─ AGENTS.md her istekte yüklenir ├─ SECURITY.md güven sınırları, ortak sırlar ├─ DEPLOYMENT.md ortamlar, CI/CD └─ SCHEMA.md ortak veri modeli (yoksa sil) <repo>/docs/ her repoda aynı düzen ├─ engineering/ nasıl: mimari, test, güvenlik… ├─ domain/ ne: sözlük, iş kuralları └─ decisions/ neden: numaralı ADR agent-kit/humans/ insanlar için └─ archive/<repo>/ taşınan eski belgeler

Platform belgeleri boş gelir

SECURITY, DEPLOYMENT, SCHEMA birer PLACEHOLDER. Workspace bootstrap'ı koddan doldurur; birden çok reponun ortak gerçeği tek kopyadır.

Kural 1: belgeye değil koda güven

Belgeler koddan geri kalır. Taşınan her iddia koda karşı doğrulanır; çelişkide kod kazanır, doğrulanamayan TODO(confirm) olur.

Kural 2: eski belge arşive, link yok

İçeriği docs/'a geçen belge repodan çıkar, humans/archive/<repo>/'a gider (tek repoda silinir, git saklar). Yeni belge ve kod oraya link vermez.

Bayatlayan insan belgesi yeniden yazılmaz: başına kısa bir "Güncel durum" notu eklenir, doğrusu repo docs/'ta. 2 MB üstü dosya git'e girmez.
Kurulum

Kurulum ve bakım

Şablona bir kez dokunulur. Ekip sonra yalnız kendi agent-kit reposuyla çalışır.

# 1. şablonu klonla, hedefe kur (repo ya da workspace) git clone <şablon adresi> ~/kod/ai-transformation ~/kod/ai-transformation/install.sh ~/kod/shop # 2. workspace ise: agent-kit yeni bir git reposu — ekibin sunucusuna push'la git -C ~/kod/shop/agent-kit remote add origin <url> && git -C ~/kod/shop/agent-kit push -u origin main # 3. ekip arkadaşı (şablona dokunmaz) mkdir shop && cd shop && git clone <agent-kit adresi> agent-kit && agent-kit/install.sh # 4. kökten başlat cd ~/kod/shop && claude

Her şey yerinde mi

install.sh <hedef> --check ya da agent-kit/scripts/check-drift.sh → check-drift: clean

Kit güncellendi

Tek repo: şablonu çek → install.sh <repo> --refresh. Workspace: agent-kit/install.sh --refresh. Yalnız kit'e ait kopyalar yenilenir.

Yeni repo / bozuk link

root/workspace.conf'a repo <klasör> <profil> satırı, sonra agent-kit/install.sh. Tekrar çalıştırmak güvenli.

Şablonun kendi testi: tests/selftest.sh tek frontend, tek backend ve workspace kurulumlarını geçici klasörlerde yapar; kapıyı, drift'i, --refresh'i ve tekrar kurulumu dener. CI'da Linux ve macOS'ta koşar.
Özet

Hatırlanacak 8 şey

1. Hedefi seç

Tek repo = kopya. Birbirine dokunan repolar = workspace + agent-kit.

2. Bootstrap'ı koştur

PLACEHOLDER'lar koddan dolar; bilinmeyen TODO(confirm).

3. Normal konuş

"Şunu ekle." Ajan skill'i kendisi seçer. Büyük iş = /write-spec.

4. Kapı otomatik

Claude'da review'lar koşmadan push/PR yok. Copilot'ta CI tutar.

5. Ekran değiştiyse

/verify-ui + gerekirse npm run test:e2e.

6. Merge senin

Ajan önerir, sen onaylarsın.

7. Kural değişecekse

Kit'te değiştir, repolarda değil. Sonra --refresh.

8. Emin değilsen

--check / check-drift.sh ve bu sunum. Ayrıntı: humans/ai-standards/.
